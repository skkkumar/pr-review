#53789 — Bound the decode paged-MQA-logits sanitize to the top-k read region +239 / -1 · awaiting first review

In simple words: before every answer step, the GPU cleaned a very big table — even when only a small part of it was used. Now it cleans only the part that is really read. Same result, much less wasted time.

What it does: since upstream #49714, every decode step scrubbed NaN/Inf from the entire [rows × max_model_len] logits workspace — 258,048 columns on GLM-5.2, 43 µs per call no matter how short the context. This PR scrubs only the front window the top-k actually reads, using a small Triton kernel, and keeps plain nan_to_num_ below 10M elements where a kernel launch costs more than it saves. It is the decode-side sibling of 51314's prefill fix — and the safe, tested successor to the older draft #50008, which dropped the fill entirely.

What has happened: opened Aug 25 with a full e2e sweep and 9 passing unit tests on MI355X. Per-call sanitize time drops 43.1 → 4.6 µs (426 → 52 ms per run; 1.82% → 0.21% of GPU kernel time); throughput +3.2% at concurrency 256, +0.6% geomean. No human review yet; rebased Aug 27.

What to expect: questions on the 10M-element crossover heuristic (how was it chosen, is it hardware-dependent), confirmation that the launch grid depends only on shapes so CUDA-graph capture stays valid, and "why not fix the #49714 scrub upstream for all platforms instead". Also expect a request to close #50008 now that this supersedes it.

Test cases added (9 cases, one new test file)

  • The scrubbed window matches nan_to_num_ exactly — checked for single-token and 2-token decode (next_n 1 and 2) and for both 1-D and 2-D sequence-length layouts, with edge lengths (empty row, full-width row).
  • Nothing past the top-k read bound is touched — the unread tail keeps its old values.
  • Each special value maps exactly like nan_to_num_: NaN → -inf, +inf → FLT_MAX, -inf → -FLT_MAX, and normal numbers are left alone.
  • Below the 10M-element crossover, the old nan_to_num_ path runs and the Triton kernel is never launched — output stays bit-identical to today's code.
  • An empty workspace is a no-op: no kernel launch at all.
  • The launch grid depends only on the row count, never on sequence lengths — so CUDA-graph capture stays valid when contexts grow between steps.

Critical findings across the four PRs

1. 50535 silently downgrades fp32-forced router compute to bf16 on ROCm. When force_fp32_compute is set and the AITER gate is on, weights are stored bf16 and the output rounds through bf16 — and the gate is platform-level, not shape-level, so a future MoE model with an untuned gate shape gets an untuned bf16 GEMM where it previously got fp32 F.linear. Defended for the three known shapes; undefended for unknown ones.

2. 51314 calls a new AITER kwarg with no guard. An AITER build older than the pin raises TypeError at runtime. 51315 shows the right pattern in the same stack (ImportError → None → gate off); the inconsistency is easy for a reviewer to spot, so offer to align them.

3. 51309's safety rests on an unasserted invariant. If any model ever had layer 0 without an indexer, skipped layers would consume uninitialized paged_kv_indices — silent garbage attention, no error. A one-line assert closes it.

4. 51315's prefill regression is real and unguarded. +65% on the prefill prologue kernel is a workload-dependent bet: net positive on the measured serving sweep, but a prefill-heavy or offline-batch deployment could regress with no off-switch besides the env flag.

5. The accuracy methodology cannot support the "unchanged" claims as stated. Sampling at temperature 1.0 produces deltas that exceed the quoted spreads (51314's RULER -0.032 vs a stated ±0.02). For the bit-identical PRs (51309, 51314) a single greedy run would prove exact equality — a stronger claim for less compute.

6. Zero upstream regression protection. Every new test skips without ROCm (+AITER, +gfx950), so upstream CI runs none of them, and the 51309/51314 unit tests are wiring-level (heavily mocked) — they would pass even if the underlying kernels misbehaved. Correctness genuinely rests on AITER's own tests plus the e2e accuracy runs.

PR 50535 — Use AITER tuned GEMM for the MoE router gate

+212 / -6 in 2 filesrocm github.com/vllm-project/vllm/pull/50535

What it does, in simple words

The MoE router gate is a tiny "traffic director" matmul that scores every expert for every token. vLLM already had a fast bf16-in, fp32-out path for it, but only on NVIDIA Hopper/Blackwell. On ROCm the gate first upcast its input to fp32; AITER has no fp32 tuned kernels for these shapes, so it silently fell through to a generic slow matmul.

This PR keeps the input in bf16 so AITER's tuned GEMM actually dispatches, and moves the fp32 cast to after the GEMM where it only touches the tiny output. It also keeps the gate weights in bf16 when force_fp32_compute is set (fp32 weights would silently disable the tuned path), and wraps the call in a custom op so torch.compile does not trace AITER's config lookup.

Anticipated reviewer questions

Why cast the output to fp32 after the GEMM instead of asking AITER for fp32 output directly? very likely
AITER keys its tuned-config table on output dtype as well as shape, and it only ships bf16-output entries for the gate shapes. Requesting fp32 out misses the table and falls back to an untuned kernel — which is exactly the slow path this PR removes. The cast now applies only to the tiny num_tokens × num_experts output instead of the full hidden-size input, so it is nearly free.
force_fp32_compute exists to protect router accuracy. Keeping weights in bf16 on ROCm defeats its purpose, no? very likely
The fp32 fallback it replaces also had bf16-representable operands — checkpoint weights are bf16, and upcasting them adds no information. The real numeric differences are the split-K reduction in the tuned kernel and the bf16 rounding of the output. Measured worst-case error is 8.8e-3 relative to the peak logit; the tests assert 2e-2 with 2x headroom, and gsm8k / RULER are unchanged within one standard error end to end.
If pushed: the top-k consistency test shows expert selection only ever differs on genuine ties inside the kernel's own error window — so routing decisions, which are all the gate output feeds, are effectively unchanged.
is_tgemm_enabled() is a platform-level gate. What if a model's gate shape has no tuned entry in AITER's table? likely
tgemm.mm itself falls back to an untuned solution for shapes missing from the table, so it still computes correctly — just without the speedup, and with bf16 rather than fp32 compute. The three shapes that matter today (GLM-5/5.2, DeepSeek-V3, Kimi-K2 routers) are all tuned and all tested.
If pushed: a per-shape eligibility check would be a reasonable follow-up if we want fp32-fallback semantics preserved for unknown shapes; today the gate is platform + weight-dtype only.
Why wrap the call in a custom op (direct_register_custom_op)? likely
torch.compile would otherwise trace into AITER's tuned-config lookup, which is data-dependent Python, and specialize on it. Registering the op with a fake impl keeps the lookup opaque to the compiler while shapes and dtypes still flow through graph capture correctly.
Why was AITER falling back to aten::mm before this change? possible
The gate upcast its input to fp32 on the CPU side before the multiply. AITER was invoked, but with fp32 operands it found no tuned kernel and fell through to aten::linear → matmul → mm. Keeping the input in bf16 is what lets the tuned dispatch hit.
Unit tests only go to M=128, but the router sees prefill batches up to max_num_batched_tokens (16k). Why? likely
The unit shapes target the latency-sensitive decode regime where the gate is skinniest and error is easiest to reason about. Large-M behavior is exercised by the e2e sweep at ISL 8192 with 16k batched tokens, where accuracy was unchanged. Extending NUM_TOKENS upward in the unit test is a cheap follow-up if wanted.
What happens with bias, or non-bf16 checkpoint weights? possible
Both are excluded by construction: the tier requires no bias (same restriction as the cuBLAS tier) and allow_aiter_router_gemm additionally checks weight.dtype == bf16 after init. Anything else falls through to the existing F.linear tier, byte-for-byte the old behavior.
Weak spots — acknowledge these proactively This is the only PR of the four that changes numerics: the gate output now carries bf16 precision even when out_dtype is fp32. The defense is layered — fp64-reference tolerance, a top-k tie-window test proving routing is stable, direct comparison against the fp32 fallback, and unchanged e2e accuracy. Also acknowledge: the unit tests exercise the custom op directly rather than GateLinear's tier dispatch, and nothing runs in upstream CI without a gfx950 runner.

PR 51309 — Skip redundant sparse index remap on non-indexer layers

+168 / -13 in 2 filesrocm github.com/vllm-project/vllm/pull/51309

What it does, in simple words

With cross-layer index sharing (GLM-5.2, index_topk_freq=4), only 21 of 78 attention layers actually recompute the shared top-k token indices; the other 57 reuse them. But the old code re-ran the index remap kernel — which translates per-request indices into global KV-cache positions — on every layer, recomputing the exact same values 57 extra times per forward pass.

This PR computes a flag at layer init ("does this layer own an indexer, or is spec decode on?") and runs the remap only when it is true. Skipped layers reuse the paged_kv_indices already written by the last indexer layer, which are bit-identical to what a re-run would produce.

Anticipated reviewer questions

How do you guarantee layer 0 owns an indexer, so the shared buffer is initialized before any layer skips? very likely
The frequency-based sharing scheme assigns indexers at layers 0, k, 2k, ... — layer 0 always owns one by construction, so the shared top-k buffer and paged_kv_indices are written before any non-indexer layer reuses them.
If pushed: there is no assert encoding that invariant today. Adding one in __init__ (or at the model level) is a cheap hardening follow-up I am happy to add.
Why does speculative decoding still need the remap on every layer? very likely
Spec decode permutes the token order in the shared buffer between layers (draft/verify reordering), so the remap inputs are not stable across layers the way they are in normal decoding. The gate is "indexer is not None OR speculative_config is not None" precisely for that case, and the test covers all four combinations.
The remap writes into shared attn_metadata.paged_kv_indices. Can a skipping layer read stale data? very likely
No. Non-indexer layers do not modify any input to the remap, so re-running it would rewrite paged_kv_indices with bit-identical values — the skipped work is provably redundant, which is also why accuracy is bit-for-bit expected-unchanged (gsm8k/RULER confirm within noise).
Why compute needs_index_remap in __init__ rather than per forward call? likely
Indexer ownership is a static property of the layer, and speculative_config is fixed for the server lifetime. A constant Python bool costs nothing per step and is CUDA-graph / piecewise-compile friendly — no data-dependent control flow enters the captured graph.
Does the default configuration change at all? likely
No. With the default index_topk_freq = 1 every layer owns an indexer, so needs_index_remap is True everywhere and the code path is identical to before. Only models configured with cross-layer index sharing (GLM-5.2 with freq 4) see the skip.
Where do 21-of-78 and the -73.3% launch reduction come from? likely
GLM-5.2 has 78 attention layers; with index_topk_freq = 4, 21 of them own an indexer. 21/78 = 0.269 launches per layer, which matches the measured 139,378 → 37,254 launch counts and the -73% GPU-time drop (2,392 ms → 646 ms per capture).
Your tests monkeypatch _forward_mla, the triton kernel, the config, and the workspace manager. Are they testing anything real? very likely
They pin the two contracts this PR introduces: the gate truth table (indexer × speculative) and "forward_mqa launches the remap exactly when gated on". Numerical equivalence does not need a unit test because skipping recomputes nothing — the values are bit-identical — and the e2e accuracy runs confirm it. I agree an integration test where a non-indexer layer consumes indices produced by a previous indexer layer would strengthen this; that needs a real ROCm multi-layer harness.
Weak spots — acknowledge these proactively The layer-0-owns-an-indexer invariant is relied on but not asserted anywhere — offer to add the assert. The unit tests monkeypatch heavily (config, workspace manager, the triton kernel, even _forward_mla), so they pin the gate contract but not real multi-layer behavior; the e2e accuracy run is what demonstrates correctness in practice. No spec-decode e2e run is included, only the unit-level gate test.

What it does, in simple words

During sparse prefill, the MQA logits buffer was allocated with torch.full(..., -inf) — an fp32 memset kernel that ran before every single logits kernel, fully serialized on the GPU stream. That was 18,162 launches and 1.25 seconds of GPU time per profiling capture, 0.89% of all kernel time.

This PR passes clean_logits=False so AITER allocates the buffer with torch.empty instead. It is safe because the buffer's only consumer, top_k_per_row_prefill, reads each row strictly inside its valid [cu_seqlen_ks, cu_seqlen_ke) range and guards its final vectorized load — the uninitialized padding bytes are never read, so the top-k result is unchanged.

PR 51315 — Fuse the DSA indexer prologue with AITER

+288 / -12 in 4 filesrocmdeepseek github.com/vllm-project/vllm/pull/51315

What it does, in simple words

Before attention, the DeepSeek Sparse Attention (DSA) indexer runs a "prologue": normalize K (LayerNorm), apply RoPE to Q and K, quantize to FP8, and write K into its cache. That took four separate GPU kernel launches, each reading and writing global memory.

This PR calls AITER's fused indexer_qk_rope_quant_and_cache kernel, which does all four steps in a single launch. It is gated to exactly the shape the kernel supports (bf16 model, head_dim 128, rope_dim 64, ue8m0 scale format); everything else keeps the old path. Because the fused kernel writes the K cache itself, the downstream indexer op is built with skip_k_cache_insert=True so the cache is written exactly once.

The trade-off to know cold: the fused kernel is 66% faster for decode but 65% slower for prefill. In a serving workload decode dominates, so the full-trace prologue time still drops 4.8% and e2e throughput improves at both input lengths.

The fused kernel is 65% slower on prefill (164 → 271 µs). Why enable it unconditionally instead of dispatching decode to fused and prefill to the old path? very likely
Because the net is positive everywhere it was measured: across the full serving trace the prologue GPU time drops 4.8% (1,093.6 → 1,041.4 ms), and the e2e sweep is positive at both ISL 1024 (+0.9%) and ISL 8192 (+0.5%) — decode dominates the prologue's total cost in a serving workload. If pushed: a decode/prefill split is a legitimate follow-up if prefill-heavy or offline-batch workloads become a priority; the gate structure makes it easy to add. AITER improving the fused kernel's large-M path is the cleaner long-term fix.
Why is the fused kernel slower at prefill in the first place? likely
It is tuned for decode-shaped launches (small token counts), where the win is removing three launch overheads and intermediate global-memory round trips. At large M the four separate kernels each get enough parallelism to saturate the GPU, so fusion's benefit disappears and its scheduling constraints cost time.
The q comparison uses rtol=0.13 — that looks enormous. Justify it. very likely
The output is fp8 e4m3, whose relative code spacing is ~12.5%; one code of drift — caused purely by a different fp32 reduction order inside the fused kernel — is exactly rtol 0.13. The comment in the test says precisely this. Crucially, the parts that persist are stricter: the K-cache bytes are compared bit-exactly (rtol=0, atol=0) and the weights at 1e-5.
The fused kernel writes the K cache itself. How do you ensure the cache is written exactly once — not twice, not zero times? very likely
SparseAttnIndexer is constructed with skip_k_cache_insert=True from the same static flag (use_fused_indexer_qk) that selects the fused path, so the two can never disagree; the flag is computed once in __init__ and nothing else writes that cache. The forward also passes k=None to the indexer op, so a double-write would fail loudly rather than silently.

The op detects that forward-context attn_metadata is not the per-layer dict yet, skips the kernel, and returns zero-filled q/weights without touching the cache. Zeros are valid placeholder values for the dummy run, whose purpose is memory sizing, not outputs.
